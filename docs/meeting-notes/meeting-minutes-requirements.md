## 一、会议背景

由于目前还在熟悉真实产线、设备和业务数据，先基于实习 JD 和初步业务理解制作了一个方向性的前端界面原型。该原型主要用于把当前理解可视化，方便与相关负责人继续对齐需求。

本次讨论确认，系统建设不一次性展开全部模块，第一阶段先聚焦 **员工绩效管理**。101 是厂房，工厂内还有多个厂房，当前先以 101厂房 为示例开始设计，后续再扩展到其他厂房。

## 二、会议主要结论

| 事项 | 会议结论 |
| --- | --- |
| 第一阶段范围 | 先做员工绩效管理，重点看员工工时、工作量、维修效率、PM01 / PM03 情况和 MTTR 异常 |
| 试点范围 | 第一版先以 101厂房 为例，后续需要支持多厂房扩展 |
| 数据分析方向 | 系统需要从数据中发现问题，例如员工维修效率差异、异常维修时间、工作量占比异常等 |
| 异常判断规则 | 当 MTTR 超过 1440 min 时，系统需要判定为异常，并提示负责人 |
| 后续建设方向 | 设备台账、设备放行、OEE / T-loss、TPM、备件、关键零部件、预测性维护等作为后续阶段展开 |

## 三、第一阶段建设内容：员工绩效管理

第一阶段需要建设一个员工绩效管理界面，用于透明展示每位员工的工作情况、维修效率和异常情况。该界面主要服务于厂房负责人、维修负责人、班组长、绩效统计人员和相关管理人员。

系统需要围绕维修和工时数据进行统计分析。核心数据包括员工姓名、工号、所属厂房、班组或区域、日期、工时、工作单号、工作类型、PM01、PM03、维修开始时间、维修结束时间、维修耗时、MTTR、设备编号、设备名称、所属产线、所属工位和负责人。

第一阶段需要重点统计总工时、总工作量、完成工单数、PM01 / PM03 数量、平均维修耗时、平均 MTTR、工作效率、个人工作量占比、异常维修记录数，以及 MTTR 超过 1440 min 的异常记录数。

## 四、员工绩效页面设计方向

员工绩效管理建议分为三个层级：绩效总览、员工列表和个人详情。

| 页面 | 主要作用 |
| --- | --- |
| 绩效总览 | 给负责人快速查看当前周期的整体情况，包括工人总人数、总工时、总工单数、平均维修耗时、平均 MTTR、异常数量、PM01 / PM03 占比和绩效排名 |
| 工人列表 | 按人展示绩效数据，包括工时、工单数、PM01 / PM03 数量、平均维修耗时、平均 MTTR、工作效率、工作量占比和异常记录数 |
| 个人详情 | 查看单个员工的详细表现，包括每日工作量、每日工时、维修耗时趋势、MTTR 趋势、参与维修设备、异常记录和工单明细 |

页面需要支持按日期范围、厂房、班组、工人、工作类型、PM01 / PM03、设备、产线和工位进行筛选。

## 五、维修效率与异常分析

会议中重点提到，需要通过数据看出哪些员工维修效率高、哪些员工维修效率低。例如，需要能够识别 1 分钟内完成的维修记录、超过 10 分钟的维修记录，以及不同员工在同一设备或同类问题上的维修耗时差异。

这些分析结果主要用于发现优秀经验、识别培训需求、判断是否存在响应慢或处理慢的问题，并为巡线管理、员工激励和管理改进提供依据。

第一阶段建议至少支持维修时间最长 Top 5、MTTR 异常 Top 5、工作量最高 Top 5、工作量最低 Top 5、效率最高 Top 5 和效率最低 Top 5。

## 六、MTTR 异常判断规则

会议确认，如果员工日期填写错误，可能导致维修时间异常变长。因此系统需要增加 MTTR 异常判断逻辑：当 MTTR 超过 **1440 min** 时，自动判定为异常。

异常记录需要进入异常列表，并提示或上报负责人。异常明细中需要展示工人姓名、工号、工单号、设备编号、设备名称、维修开始时间、维修结束时间、MTTR、异常原因、处理状态和负责人。默认异常原因可标记为“疑似日期填写错误”。

第一版提醒方式可以先采用系统内提示，后续再考虑邮件、企业微信或其他通知方式。

## 七、后续需求方向

除第一阶段员工绩效管理外，会议中还讨论了后续系统需要覆盖的其他方向。

| 模块 | 后续需求方向 |
| --- | --- |
| 厂房总览 | 以 101厂房 为模板，展示产线数、设备数、供应商数、放行状态、资产分类、公用设备、OEE / T-loss 和 TPM 概览 |
| 设备台账 | 维护设备编号、名称、厂房、产线、工位、供应商、联系方式、采购金额、资产类型、放行状态和使用状态 |
| 设备放行 | 放行指验收通过并允许上线使用。当前存在未放行但已经在使用的设备，后续系统需要识别并提醒 |
| OEE / T-loss | OEE 和 T-loss 都是需要连接数据源的指标，后续需要按厂房、产线、设备进行指标分析和趋势查看 |
| 公用设备 | 公用设备指多个产线或多个工位共用的设备，后续需要分析其损失情况、维修频率和指标趋势 |
| 备件与零部件 | 后续需要管理备件数量、料号、品牌、使用情况和成本，并支持员工查找备件 |
| 关键零部件 | 后续需要标记相机、传感器等关键零部件，记录更换和故障时间，用于寿命分析 |
| 预测性维护 | 基于故障时间、更换时间和平均寿命，提前提醒负责人准备维护或更换 |
| TPM | TPM 需要单独做界面，展示哪些设备计划做、正在做、还没做，以及月度完成情况和人力需求 |
| 样品计划 | sample 指样件/样品生产计划，后续需要支持日期时间安排、相关设备或产线、计划状态和工作计划关联 |

## 八、已确认业务口径

101 指厂房，当前先以 101厂房 为例开始做。设备金额小于 9.5 万元的属于费用类采购设备，不属于固定资产；设备金额大于 9.5 万元的属于固定资产，等于 9.5 万元的边界规则后续需要确认。

放行指验收通过并允许上线使用。OEE / T-loss 是需要连接数据源的指标。公用设备指多个产线或多个工位共用的设备。TPM 需要独立界面，不和普通维修混在一起。sample 指样件/样品生产计划。
